# telegram-image-delivery Specification

## Purpose

Define reliable and privacy-preserving delivery of generated images through Telegram so a completed generation survives restarts and reaches only the chat that requested it.

## Requirements

### Requirement: Generated images are queued for their originating chat
The system SHALL create a durable outbound image intent only for the trusted chat and message associated with the invoking accepted Telegram update. The agent and image provider MUST NOT choose an arbitrary destination. The intent SHALL retain the validated image bytes and supported media type needed for delivery without embedding them in a text message.

#### Scenario: Image is published from a private-chat turn
- **WHEN** image generation completes during an accepted private-chat turn
- **THEN** the image intent targets that private chat and replies to its originating message

#### Scenario: Image is published from a group turn
- **WHEN** image generation completes during an accepted group-chat turn
- **THEN** the image intent targets that group and does not target the invoking user's private chat or another group

#### Scenario: Model prompt requests another destination
- **WHEN** model-produced arguments or generated content attempt to select a different chat
- **THEN** the system ignores or rejects that destination and does not enqueue media outside the trusted turn context

### Requirement: Image delivery is durable and idempotent
The system SHALL persist a generated-image intent before acknowledging it as queued, lease it for delivery, and preserve it across service or container restarts. Repeating publication for the same accepted update and tool invocation MUST NOT create a second outbound image. A delivery retry SHALL reuse the stored image and MUST NOT invoke image generation again.

#### Scenario: Service restarts after queueing
- **WHEN** the service restarts after an image tool reports `queued` but before Telegram confirms delivery
- **THEN** the pending image remains eligible for delivery using the previously generated bytes

#### Scenario: Publication is repeated
- **WHEN** the same generated-image publication is attempted again for the same update and tool invocation
- **THEN** the durable outbox contains only one deliverable image intent

#### Scenario: Telegram delivery fails transiently
- **WHEN** Telegram temporarily rejects or cannot receive a leased image intent
- **THEN** the system records a bounded error, schedules delivery retry, and does not regenerate the image

### Requirement: The queued explanation precedes the generated photo
The system SHALL retain generated photo bytes durably while holding their delivery until the surrounding turn has queued its final text response. Pending text intents SHALL be leased before pending photo intents so the user receives the queued explanation before the image without making photo retries block later text.

#### Scenario: Final response is delivered before the generated photo
- **WHEN** a turn queues a generated photo during tool execution and then queues its final assistant response
- **THEN** Telegram receives the final text response before the generated photo

#### Scenario: Crash before final response queueing
- **WHEN** the process stops after durable photo queueing but before final response queueing
- **THEN** startup marks the interrupted update and releases the held photo without regenerating it

### Requirement: Telegram receives a bounded photo upload
The system SHALL upload a queued generated image as a Telegram photo using its stored bytes and media type, associated with the originating message. It SHALL reject an image that exceeds the configured Telegram-compatible byte limit before queueing, and SHALL persist Telegram's returned message identifier only after a successful upload.

#### Scenario: Telegram accepts the generated photo
- **WHEN** the delivery worker uploads a valid queued image and Telegram confirms the photo message
- **THEN** the outbox marks the intent sent and stores the returned Telegram message identifier

#### Scenario: Generated image exceeds the delivery limit
- **WHEN** validated generated bytes exceed the configured Telegram photo limit
- **THEN** the system rejects publication before adding an image intent and does not attempt a Telegram upload

#### Scenario: Telegram rejects an upload
- **WHEN** Telegram returns a failed response for a queued photo
- **THEN** the intent remains unsent and eligible for bounded-backoff retry without being reported as delivered

### Requirement: Image and text outbox intents coexist safely
The delivery worker SHALL support both existing text intents and generated-image intents without changing text rendering, reply markup, parse mode, leasing, retry, or sent-state behavior. A failed image delivery MUST NOT corrupt or convert another text or image intent.

#### Scenario: Outbox contains text and image intents
- **WHEN** the delivery worker processes a mixture of pending text responses and generated images
- **THEN** each intent uses its corresponding Telegram operation and retains its own delivery state and retry count

#### Scenario: Existing text response is delivered
- **WHEN** a pending text intent created before this change is leased
- **THEN** it is sent with the same text, formatting, reply behavior, and deduplication semantics as before

### Requirement: Generated media follows retention and privacy controls
Pending generated-image bytes SHALL be included in application backup and restore so acknowledged queueing remains recoverable. Sent or cancelled generated bytes SHALL be erased when the configured retention cutoff is applied. Image bytes and private image content MUST NOT appear in logs, health output, delivery errors, or text fields used for diagnostics.

#### Scenario: Database is backed up with a pending image
- **WHEN** an application backup is created while a generated image is pending and then restored into a fresh runtime
- **THEN** the restored image intent contains the bytes and metadata required to resume delivery

#### Scenario: Retention runs after image delivery
- **WHEN** a sent or cancelled generated-image intent is older than the configured retention cutoff
- **THEN** its binary image content and private error detail are removed while minimal delivery metadata may remain

#### Scenario: Operator inspects diagnostics after a photo failure
- **WHEN** image delivery health or logs report a Telegram upload failure
- **THEN** the diagnostic output contains no generated bytes, prompt content, caption content, or authentication value
