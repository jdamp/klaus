# Design

## Context

See `proposal.md` for motivation and `specs/image-generation/spec.md` plus `specs/telegram-image-delivery/spec.md` for the behavior contract.

Klaus currently exposes application and MCP tools through `AgentToolCatalog`. Tool definitions are created per session, but trusted Telegram update data is available only while `AgentTurnHandler` executes a turn. The memory capability bridges that lifetime with a session-keyed context registry. The image tool similarly needs the trusted chat, message, update, and tool-call identities at execution time; none of those destination values may come from model arguments.

Outbound delivery currently consists only of text rows in `outbox_messages`. `OutboxWorker` leases each row, calls `sendMessage`, and retries transient failures. SQLite backup and retention already cover this table. Telegram inbound visual-input work is present but uncommitted in the working tree; it adds media download APIs and must not be overwritten or conflated with outbound generation.

Pi 0.85.1 has a provider-neutral `ImagesModels` abstraction, but its bundled image-provider catalogue contains only OpenRouter. Pi's `openai-codex-responses` chat adapter neither exposes the Codex image tool nor parses image-generation output. The installed Codex CLI declares image generation stable and implements it as a separate request to the active provider's `images/generations` endpoint. For ChatGPT OAuth, Codex uses `https://chatgpt.com/backend-api/codex/images/generations`, `gpt-image-2`, and provider-owned account-routing headers. A live check is currently blocked by the local OAuth credential requiring a new login.

## Goals / Non-Goals

**Goals:**

- Give application code and agent tools one provider-neutral text-to-image contract.
- Confine Codex endpoint, model, OAuth-routing, request, and response behavior to one replaceable adapter.
- Reuse Pi's protected credential resolution and refresh path without reading its authentication file.
- Queue generated bytes durably before returning a successful tool result.
- Extend the existing outbox and Telegram client without regressing text delivery or inbound visual messages.
- Bound prompt size, network time, encoded response size, decoded image size, SQLite growth, and audit output.
- Preserve determinate cancellation semantics around a completed image tool call.

**Non-Goals:**

- Feed generated image bytes back into the conversational model or persist them in the Pi session.
- Support image editing, source-image references, transparent-background controls, quality/size controls, multiple outputs, captions, or arbitrary destination chats in the first version.
- Expose Codex's image endpoint or a generic HTTP operation to the model.
- Add OpenRouter credentials or a second image backend in this change.
- Guarantee that an externally generated image can be recovered if the process dies after the provider completed but before the SQLite enqueue committed.
- Treat an image-generation request as a transaction spanning the provider and Telegram; neither external system offers such a transaction.

## Decisions

### 1. Define a small application-owned image-generation port

Add an image-domain contract equivalent to:

```ts
type ImageGenerationRequest = { prompt: string };
type GeneratedImage = {
  bytes: Uint8Array;
  mediaType: "image/png" | "image/jpeg";
};

interface ImageGenerator {
  generate(request: ImageGenerationRequest, signal: AbortSignal): Promise<GeneratedImage>;
}
```

The contract deliberately excludes provider, model, endpoint, authentication, quality, size, and raw response fields. Backend selection belongs to application composition. An `ImageGenerationProvider` implements the existing capability-provider lifecycle, exposes `generate_image`, invokes the port, and publishes the result. The tool accepts only `prompt`, returns bounded queue metadata, and never returns base64 or bytes to the model.

Configuration uses a discriminated composition-only backend block, conceptually:

```yaml
imageGeneration:
  backend:
    type: openai-codex
  promptMaxBytes: 16384
  requestTimeoutMs: 180000
  maxResponseBytes: 16777216
  maxImageBytes: 10485760
```

The first backend fixes the image model and generation defaults inside its adapter. Future backend variants may have nested operator-only settings, but they do not change `ImageGenerator` or the tool schema. Omitting `imageGeneration` means no provider is registered and no tool is exposed.

Alternatives considered:

- Using Pi's `ImagesModels` directly is not sufficient because its installed image catalogue has no Codex provider and its separate collection cannot reuse `ModelRuntime`'s private credential store without custom resolution.
- Putting `provider`, `model`, `size`, or `quality` in tool arguments would leak backend concerns and let model output expand cost and compatibility choices.
- Returning an image content block from the tool would duplicate large base64 data into Pi messages and SQLite session entries, require an image-capable chat model, and weaken retention boundaries.

### 2. Implement Codex as an isolated backend adapter using Pi-resolved auth

`CodexImageGenerator` receives the existing `ModelRuntime` and an injected `fetch`. For every request it calls `runtime.getAuth("openai-codex", { signal })`, allowing Pi to serialize refresh and persist rotated credentials. It never opens `authPath`. The adapter derives the ChatGPT account-routing identifier from the resolved access token in the same provider-specific layer that constructs Codex headers; decoded claims are neither stored nor returned. Missing or malformed routing identity is an authentication failure.

The adapter sends one non-following JSON POST to the fixed Codex image-generation URL with these provider-owned values:

- model `gpt-image-2`
- `background: "auto"`
- `quality: "auto"`
- `size: "auto"`
- no caller-selected image count
- bearer authorization, ChatGPT account routing, an application originator, and a correlation header

It incrementally reads at most `maxResponseBytes`, parses exactly one `data[].b64_json` result, bounds the encoded value before decoding, and rejects non-canonical/invalid base64. It then checks decoded size and PNG/JPEG magic bytes rather than trusting response metadata. Provider request IDs may be retained only as bounded operational metadata; response bodies and generated bytes never enter errors or logs.

The capability's startup check resolves auth but does not create a paid image. Calls update privacy-safe health state on authentication, compatibility, transport, and response failures; a later successful call recovers health. Tool definitions remain available while a configured backend is degraded so credential repair does not require recreating every session.

Alternatives considered:

- Spawning `codex exec` would use another process and auth home, make tool selection nondeterministic, write temporary artifacts, and spend an extra conversational-model call.
- Copying or parsing Pi's persisted credential file would bypass locking and refresh semantics and violate the runtime authentication boundary.
- Patching `node_modules` to add a built-in Pi provider is not maintainable. Upstream Codex support in Pi can later replace this adapter behind the same port.
- A startup generation probe would consume quota and create unwanted content; auth resolution plus last-call health is sufficient for an optional capability.

### 3. Introduce a provider-independent trusted turn-context reader

Add an application-owned turn context containing `chatId`, `messageId`, `updateId`, `senderId`, and optional sender label. `AgentTurnHandler` installs it under the active session before prompting and clears it with a token in `finally`, matching the current concurrency-safe memory pattern. The image capability receives only a read interface and its session binding, then resolves context at tool execution time.

The tool callback also receives Pi's `toolCallId`. The publication identity is derived from trusted `updateId` plus `toolCallId`; destination and reply identifiers never appear in tool parameters. Coordinate this context addition with the current memory registry instead of moving or overwriting the uncommitted visual-input changes. A small shared registry or a base-context reader layered beside memory is preferable to importing image code from `src/memory`.

Alternatives considered:

- Capturing destination in the tool definition when a session is created is incorrect because one session handles many later updates.
- Passing chat IDs as model-visible arguments creates cross-chat messaging authority.
- Publishing from `AgentTurnHandler` by scraping Pi tool-result messages couples turn orchestration to one tool's result shape and loses bytes unless they are persisted in conversation state.

### 4. Generate, validate, and enqueue inside one audited tool execution

The `generate_image` executor performs these stages:

1. Validate and byte-bound the prompt before provider access.
2. Resolve trusted turn context and check whether the publication identity already exists.
3. Invoke the configured `ImageGenerator` with the combined turn/deadline signal.
4. Validate the provider-neutral result again at the publication boundary.
5. Insert the image outbox intent with a unique dedupe key.
6. Return `{ status: "queued", count: 1 }` only after insertion, treating an already-existing dedupe key as already queued rather than creating another delivery.

Extend the native-tool execution envelope only as needed to pass `toolCallId`, trusted `updateId`, and safe audit metadata. Audit the bounded prompt and final queue status according to existing tool policy, but summarize the generated result as MIME type and byte count; never audit image bytes or base64. The Pi session persists the ordinary tool call and small queue result, not the media.

If cancellation wins before enqueue, no image intent is created. Once enqueue commits, later turn cancellation does not remove it: the tool action completed and the existing conversation contract preserves completed tool outcomes. A crash after remote generation and before enqueue remains indeterminate and is not automatically replayed, avoiding accidental duplicate cost.

Alternatives considered:

- Enqueueing after the entire agent turn completes loses a completed image on later model failure or cancellation.
- Sending Telegram directly from the tool forfeits retry, backup, idempotency, and shutdown behavior.
- Automatically rerunning an indeterminate generation may consume quota and generate a different or duplicate image.

### 5. Extend the outbox with discriminated text and photo intents

Add an additive SQLite migration with a delivery kind, binary payload, and media type while retaining the existing non-null text column for migration compatibility. Existing rows default to `text`; photo rows use an empty legacy text value. Repository APIs expose discriminated unions so callers cannot construct a photo with text-only fields or a text message with binary content. On lease, the repository validates the stored combination and fails closed on malformed rows.

Conceptually the variants are:

```ts
type OutboxDraft =
  | { kind: "text"; text: string; parseMode?: "HTML"; replyMarkup?: ... }
  | { kind: "photo"; bytes: Uint8Array; mediaType: "image/png" | "image/jpeg" };
```

Both variants retain common identity, chat, reply, sequence, lease, attempts, availability, Telegram message ID, and timestamps. The existing unique dedupe key provides publication idempotency. SQLite BLOB storage is selected because queue acknowledgement must survive restart and the current backup must remain self-contained. `maxImageBytes` caps per-row growth. Retention additionally sets the binary payload and media type to null for old sent or cancelled rows.

Alternatives considered:

- A filesystem spool plus path reduces database size but requires atomic coordination, separate backup/restore, orphan cleanup, and persistent-volume path policy.
- Base64 in a text/JSON column expands storage and risks accidental diagnostic rendering.
- A separate image-outbox worker duplicates lease, retry, health, and shutdown logic.
- Rebuilding the whole table for strict cross-column checks increases migration risk for in-flight rows; additive columns plus repository validation preserve existing deployments.

### 6. Dispatch photo intents through Telegram multipart upload

Broaden the delivery sender contract to support text and photo operations. `OutboxWorker` switches on the leased discriminant, retaining the same lease, exponential backoff, sent transition, and health behavior. A failed photo retries from the stored BLOB and never calls the generator.

`TelegramHttpClient.sendPhoto` constructs `FormData` with `chat_id`, a `Blob` and deterministic extension, and JSON-encoded `reply_parameters`. It does not manually set the multipart `Content-Type`, so `fetch` supplies the boundary. It reuses the existing Telegram envelope handling and returns `message_id` for the outbox sent transition. The image byte limit is enforced before enqueue and defensively before upload.

The photo is durably stored during the tool call but held until the surrounding turn queues its final assistant text. The delivery worker prioritizes pending text intents over photos, so the user receives the explanation that the image is queued before the image itself. If the process dies before the turn finishes, startup marks the interrupted update indeterminate and releases its held photo; a completed turn releases the photo in its finalization path. A failed photo upload does not block later text because retries reuse the stored BLOB independently.

Alternatives considered:

- Embedding a data URL in `sendMessage` is unsupported and exposes payload data as text.
- Sending generated images as documents loses the intended in-chat photo presentation; document fallback can be a future capability if larger outputs are required.
- Blocking every later text intent behind a failing photo can make an entire chat appear unavailable for one media-specific Telegram failure.

### 7. Keep optional capability failure isolated

Invalid static image configuration fails configuration parsing. When valid optional configuration exists but provider authentication or network access is unavailable, application startup continues unless that same provider is independently required by the configured chat model. Capability health becomes degraded and calls return a bounded failure. No provider body, prompt, image, token, or account identifier is included in health.

The generic capability lifecycle closes no shared runtime resources. Shutdown cancellation propagates through active generation. Already queued rows remain pending for the next process, consistent with text delivery.

Alternatives considered:

- Making image readiness part of core readiness would take ordinary household chat offline for an optional feature.
- Removing the tool from sessions while degraded prevents recovery without session recreation and can lead the model to silently claim it lacks a configured feature.

### 8. Verify boundaries with fixtures before a live smoke test

Use an injected image generator for capability tests and injected `fetch` for Codex and Telegram tests. Cover prompt/schema bounds, trusted destinations, cancellation races, duplicate publication, provider auth resolution, redirect rejection, response streaming bounds, exact-one-image parsing, base64 and magic-byte validation, error redaction, and health recovery.

Add migration tests from the prior schema, text/photo repository union tests, mixed outbox leasing and retry tests, multipart `sendPhoto` assertions, retention erasure, and backup/restore of a pending BLOB. Session tests verify that the tool is absent when disabled, present when configured, contains no provider parameters, and stores only its small structured result. Re-run inbound visual-input tests to prove the outbound additions do not change Telegram download behavior.

A staged live smoke test occurs only after re-authenticating `openai-codex`. It generates disposable non-sensitive content, verifies one photo and its reply target, restarts with a queued photo, checks retry without regeneration, and scans logs, health, audits, sessions, and text columns for credentials and image payloads.

Alternatives considered:

- Live-only tests consume quota, depend on OAuth state, and cannot deterministically exercise size, malformed response, redirect, or crash boundaries.
- Unit fixtures alone cannot detect a changed private Codex route, so a deployment smoke check remains required.

## Risks / Trade-offs

- **Codex's ChatGPT image route is implemented by the official CLI but is not currently exposed by Pi's public image-provider catalogue** → Keep every route and payload assumption in one adapter, record the Codex version used for fixtures, fail closed on response drift, and prefer upstream Pi support when available.
- **The adapter must derive an account-routing claim from a Pi-resolved access token** → Keep claim handling inside the Codex adapter, never read the credential file, never persist or log the claim, and test malformed-token redaction.
- **OAuth refresh is currently stale in the local environment** → Require a fresh login before live validation; deterministic tests use fake resolved auth and make no real provider request.
- **SQLite backups grow with pending photos** → Cap each image at the Telegram-compatible limit, generate one image per invocation, erase old sent/cancelled BLOBs through retention, and document storage sizing.
- **A process can die after paid generation but before durable enqueue** → Mark the surrounding update indeterminate through existing behavior and never auto-replay generation.
- **Telegram may reject an otherwise valid provider image** → Validate format and byte size before queueing, retain the BLOB for bounded-backoff retry, and expose a privacy-safe delivery degradation.
- **The generated photo is enqueued before the final assistant response** → Persist it immediately for crash safety, hold it until final response queueing, and prioritize text leases so the user sees the queued explanation before the photo without making image retry block later text.
- **Generated-image prompts and outputs can be sensitive** → Keep bytes only in the bounded outbox/backup retention path, avoid tool-result duplication, and apply existing retention to bounded prompt audits and generated media.
- **Image and visual-input work touch overlapping Telegram/configuration files** → Rebase carefully around current uncommitted changes and run both inbound and outbound media suites before formatting or broad edits.

## Migration Plan

1. Land the additive outbox migration and discriminated repository support first; verify all legacy text rows and delivery tests behave unchanged.
2. Add Telegram photo upload and mixed outbox dispatch behind tests, with no image producer enabled.
3. Add trusted turn context, the neutral image port, the Codex adapter, and the disabled-by-default capability configuration.
4. Update examples, deployment documentation, storage guidance, and privacy-safe operational diagnostics.
5. Re-authenticate the configured `openai-codex` provider outside the repository, enable image generation in staging, and run the disposable live smoke checks.
6. Back up SQLite, deploy one instance, verify core readiness remains healthy, and inspect capability and delivery health.

Rollback first removes or disables `imageGeneration`, then allows pending photo intents to deliver or explicitly cancels them before deploying an older binary. This prevents an older text-only worker from interpreting an unknown pending photo row as an empty text message. Additive columns and already-sent rows may remain in SQLite; the prior code uses explicit text columns and ignores non-pending sent rows. Restore the pre-deployment database backup only if schema rollback is required, accepting that post-backup conversation and delivery state would be lost.
